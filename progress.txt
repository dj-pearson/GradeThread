## Session Notes (2026-05-27) — iOS iPad layout polish (US-193)
The iPad layout from US-171 was two-column. This pass restructures
into three columns with Photos.app drag-drop + multi-window.

What landed:
- ContentView's SidebarSplitView restructured to use
  `NavigationSplitView(sidebar:content:detail:)`. Sidebar carries
  the section nav, content shows the active section's main view
  (real InventoryListView for inventory; placeholders for others),
  detail hosts a NavigationStack that resolves value-based pushes
  via `.navigationDestination(for: LocalInventoryItem.self)` →
  ItemCanvasView.
- SwiftUI's three-column splitter auto-collapses to two-column on
  iPad portrait + Slide Over, satisfying the AC's portrait spec
  without per-orientation code. iPhone compact width still routes
  to TabBarShell.
- InventoryListView's NavigationLink converted to value-based
  (`NavigationLink(value: item)`) so the same row works in both
  TabBarShell's per-tab NavigationStack AND the detail column's
  stack.
- Per-section NavigationPath retained on AppRouter so deep
  navigation in the detail column survives a sidebar switch.
- Detail landing view shows a 'Pick an item' placeholder with
  section-aware icon + copy.

Info.plist:
- UIApplicationSceneManifest with UIApplicationSupportsMultipleScenes=
  YES. SwiftUI's WindowGroup handles the rest — users open a second
  window via the App Switcher (drag from Dock or long-press 'New
  Window'). No SceneDelegate needed.

Drag-drop:
- ios/GradeThread/Inventory/PhotosDropHandler.swift processes
  dropped UIImages through the same PhotoCompressor pipeline the
  camera flow uses; .acceptsImageDrops View modifier wraps
  .dropDestination(for: Data.self) and decodes JPEG/PNG payloads.
- InventoryListView's List accepts image drops + maps captures onto
  the first available slots (front → back → tag → detail → defect
  1/2/3), then presents PhotoIntakeView with the pre-staged photos
  via a new init(initialPhotos:) overload — non-destructive, the
  default init still works for the camera-first path.

Tests in PhotosDropTests cover the compressor pipeline (empty, single,
multi-image with order preservation), .source=.library stamping, and
the PhotoIntakeView initial-photos init compiling cleanly.

## Session Notes (2026-05-27) — iOS Realtime channel (US-198)
Phase 2 of US-172's sync layer — sale + listing edits now stream into
the SwiftData cache the moment they hit the server. Pull-to-refresh
still works as a fallback; this just removes the wait when the app's
already open.

What landed:
- ios/GradeThread/Persistence/RealtimeService.swift — owns a per-user
  inventory_items channel via supabase-swift's channel.postgresChange
  AsyncStream. Filter scoped to .eq('user_id', userId) so other
  users' rows never reach the client. Status observation via
  channel.statusChange maps SDK states (.subscribed / .subscribing /
  .unsubscribed / @unknown) to a UI-friendly Phase enum (.idle /
  .subscribing / .subscribed / .reconnecting / .disabled).
- SyncEngine grew applyRealtimeInventoryUpsert(record:Data) and
  applyRealtimeInventoryDelete(id:) — reuse the same
  RemoteInventoryItem wire shape the polled pull decodes against,
  same @MainActor ModelContext, same ConflictPolicy. Garbage payloads
  log + drop instead of crashing the listen loop.
- RemoteInventoryItem / RemoteItemPhoto promoted from private to
  internal so the realtime service can reach them.
- SyncStatusStore.Phase gains .reconnecting. SyncStatusBar renders
  an orange 'Reconnecting…' chip with a small ProgressView. The
  banner only flips into reconnecting from .idle so an active sync
  / pending / offline banner wins.

Lifecycle:
- ContentView opens the channel on .signedIn + on scenePhase →
  .active (covers cold start + foreground).
- Pauses on .background to save battery + cellular data.
- Tears down on .signedOut so the next user's session starts clean.
- RealtimeService.isEnabled UserDefaults-backed (default ON).
  Flipping false in Settings immediately calls stop() and tears the
  channel down.

Settings:
- New 'Live updates' Toggle in SettingsPlaceholder
  (RealtimeToggleSection). UserDefaults-backed, default ON, footer
  explains the battery trade-off.

Tests in RealtimeTests cover SyncStatusStore.Phase.reconnecting,
applyRealtimeInventoryUpsert insert + update paths (title + status
flipping through ConflictPolicy), applyRealtimeInventoryDelete row
removal, and garbage-JSON resilience. Actual channel + statusChange
streams aren't hermetically testable without a real Realtime socket
— first TestFlight build is the live verification.

## Session Notes (2026-05-29 cont.) — Build-time prerender (US-292, US-298)

Shipped the keystone of the SEO program: every static public page is now
prerendered to crawlable HTML at build time. This makes the <title>,
description, canonical, OG/Twitter, and JSON-LD visible to AI crawlers
that don't run JS (GPTBot, ClaudeBot, PerplexityBot, etc.).

Approach + the big constraint:
- NO headless browser is used. There is no Chromium/puppeteer/playwright
  in this container, and a Chromium download would be fragile in
  CI/Cloudflare builds. So the prerender is a BROWSERLESS Vite SSR pass.
- CONFIRMED (probed directly) that react-helmet-async v3.0.0 does BOTH:
  renders nothing into a server head sink (ctx.helmet came back empty)
  AND injects no <script> client-side. So helmet cannot drive the
  prerendered <head>. Instead the <head> is built deterministically from
  the route registry + json-ld.ts.
- Bonus discovery: LaunchBanner + CookieConsent were already written to
  "render nothing on the server pass" — the codebase was designed for
  prerendering.

What landed:
- src/prerender/entry-server.tsx: renders each public page inside a
  StaticRouter + HelmetProvider + QueryClientProvider via renderToString.
  Pages are mapped explicitly (not via the lazy app router) so the SSR
  bundle never pulls in the auth/dashboard/supabase graph. Exports
  PRERENDERABLE_PATHS for the sync guard.
- src/prerender/head-builder.ts: buildHeadTags(route) (title/desc/
  canonical/robots/OG/Twitter + JSON-LD), jsonLdForRoute(path) (mirrors
  what each page's <SEO> emits: landing = Org+WebSite+SoftwareApp+FAQ;
  legal = Org+Breadcrumb), and stripHeadTagsFromBody() — removes the
  inline Helmet <title>/<meta>/<link canonical> the v3 fork leaks into
  the SSR body so they don't end up inside <div id=root>.
- scripts/prerender.mjs: runs after `vite build` (wired into npm run
  build + a standalone `npm run prerender`). Loads the above via Vite
  ssrLoadModule, asserts registry<->entry are in sync (build fails if a
  route is in one but not the other), then for each route injects body
  + head into dist/index.html between the new prerender:head markers and
  the #root prerender:body marker, writing dist/<route>/index.html.
- index.html: added <!-- prerender:head:start/end --> markers around the
  default head tags and <!--prerender:body--> inside #root. The defaults
  remain the SPA fallback for any non-prerendered route.
- src/pages/landing-faqs.ts: FAQ data extracted to its own module so both
  landing.tsx and head-builder share it (and landing stays a
  components-only file for the react-refresh lint).
- package.json build script: "tsc -b && vite build && node
  scripts/prerender.mjs".

Not cloaking, no hydration mismatch: identical HTML to all visitors;
main.tsx uses createRoot (not hydrateRoot) so the SPA cleanly re-renders
over the static shell. SPA fallback intact (dist/_redirects /* ->

## Session Notes (2026-06-02) -- US-267 edge input hardening

US-267 (Security: request body-size limits + schema validation on edge inputs)
-- IMPLEMENTED, passes=true.

Body-size guard: src/middleware/body-limit.ts. Rejects oversized payloads with
HTTP 413 off the Content-Length header BEFORE the handler buffers the body.
Per-route caps resolved by path: 15MB for image-upload prefixes (/api/grade,
/api/v1/grades, /api/flipdesk/{grading,images,disclosure,autolister},
/api/content/images), 256KB for every other JSON-only /api/* endpoint
(capForPath() does boundary-safe prefix matching so /api/gradebook != /api/grade).
Registered once as app.use("/api/*", bodyLimit) right after securityHeaders;
GET/HEAD/OPTIONS skip it, and /health + the OPTIONS preflight never reach it.

Shared validation helper: src/lib/validation.ts.
- validateJson(c, zodSchema) -> {ok,data} | {ok:false,status,error,details}.
  Enforces application/json Content-Type (415 otherwise), parses safely (400 on
  malformed JSON), runs the schema, flattens ZodError to "path: message"
  details, and NEVER 500s on bad input. zod added to deno.json import map
  (esm.sh/zod@3.23.8).
- decodeBase64Image(input, declaredMime, maxBytes): allowlists the MIME
  (jpeg/png/webp/gif), accepts raw base64 or data: URLs, validates the base64
  charset, rejects on approx-decoded size BEFORE allocating, then sniffs magic
  bytes and requires them to match the declared MIME (so a payload can't claim
  image/png while shipping an SVG/exe). 10MB/image default cap.

Reference conversions (per AC "at least grade-submit and flipdesk grading-submit"):
- flipdesk grading /submit + /validate now validate through a strict zod schema
  (items[].inventory_item_id UUID, tier enum, .strict() rejects smuggled fields,
  1..200 batch bound), replacing the hand-rolled parseSubmitBody (removed; the
  now-unused isGradeTier import dropped). Tightens inventory_item_id from
  "non-empty string" to UUID -- correct since item ids are gen_random_uuid().
- api-v1 /grades base64 branch routed through decodeBase64Image before
  forwarding bytes to storage/Claude Vision (was a raw atob that could 500).
- grade /submit (multipart) is covered by the body-limit cap + its existing
  formData() try/catch -> 400 content-type enforcement.

Tests: src/tests/body-validation_test.ts (15 Deno.test cases) -- capForPath
