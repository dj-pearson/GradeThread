The blockers, and how each was closed

Ranked by how likely each one was to end the review. Kept in full because the reasoning is what a reviewer would ask about, and because the second one is the kind of gap that reopens quietly.

1

The extension reads eBay listing pages and sends them to your servers

Closed

The unified extension injects a content script into every eBay domain, pulls the gallery photos and title out of the page, and posts them to functions.gradethread.com for grading. Your own code comment calls them "scraped gallery photos." The server then fetches those eBay-hosted image URLs itself.

eBay's API License Agreement says eBay content comes through the API and not by other means. A reviewer who installs your extension finds this in about two minutes, and it reframes the whole application: you are asking for more API access while taking data outside the API. It is also the finding most likely to put your existing production keyset at risk, not just the increase.

Fix, now shipped Pick one before submitting. Either drop eBay from the extension's content-script matches and host permissions so the overlay simply does not run on eBay, or rebuild the eBay path to call the Browse API by item id (the item id is in the URL) instead of reading the DOM. The second is more work and needs the buy.browse scope, but it keeps the feature.

2

Account deletion leaves eBay buyer data behind

Closed

The handler is well built: it verifies the signature, dedupes by notification id, returns 500 so eBay retries rather than falsely acknowledging, and writes a compliance log row. But all it actually does is set marketplace_connections.is_active = false and null the tokens.

Most deletion notifications are for buyers, not for the seller who connected. When eBay tells you a buyer closed their account, you keep their username in four tables and delete nothing. That is the substance of the requirement, and it is the part a reviewer tests.

Fix, now shipped Extend the handler to null or hash buyer_username in sales, marketplace_offers, marketplace_post_sale_cases and flipdesk_ebay_orphan_sales for the deleted eBay user, in the same transaction shape, with the same retry-on-error rule. Keep the sale row itself (you need it for the seller's books); remove the person.

3

You cannot show your call volume, and that is the stated gate

Closed

eBay's page is blunt about it: they will not approve an application with no usage, and the form asks for a call volume estimate. There is no counter anywhere. The eBay client has excellent throttling but never records that a call happened, so you have no daily number, no per-API breakdown, and no basis for a forecast that is not a guess.

Fix, now shipped Add one counter inside ebayFetch in lib/ebay-client.ts, the single choke point every eBay request already passes through. Record date, API family (Inventory, Fulfillment, Browse, Taxonomy, Account, Finances), endpoint, and status. Roll it up daily. Run it for two weeks before you submit so the form carries a measured number and you can attach the chart.

The eBay developer portal also exposes your own consumed limits through the Analytics API getRateLimits call. Pull that on a cron too; it gives you eBay's own view of your usage, which is the number the reviewer will compare yours against.

4

eBay-derived data never expires

Closed

Category aspects have a 30-day time limit. Nothing else does. Style-code observations harvested from other sellers' listings, mirrored eBay listings, payouts and search terms all sit in the database forever, and none of the fifty job routes is a retention sweep.

Fix, now shipped Add one jobs-ebay-retention.ts cron with a stated policy per table and put the policy in your privacy page. A defensible starting point: comp and observation data from other sellers' listings expires at 90 days, the seller's own mirrored listing and order data lives as long as their account, and everything goes on account closure.

Closed

Ask for Logistics and sold data as two separate requests

Closed

Sell Logistics is a normal restricted API and a well-argued growth check usually gets it. Buy Marketplace Insights is a different animal: eBay grants sold-price data rarely, and mostly to established partners with volume behind them. Bundling them means one weak ask can drag down the strong one.

What is already clean

Worth knowing so nobody re-audits it, and worth citing in the application. Several of these are stronger than what eBay expects.

The deletion endpoint is built correctly, not just present

The GET handshake hashes challenge code, verification token and endpoint URL in the right order with the right encoding. The POST verifies eBay's ECDSA signature over the raw body before any database write, after a past bug let anyone mass-disconnect sellers. A failed deactivation releases the idempotency claim and returns 500 so eBay retries, rather than acknowledging a deletion that did not happen. Every notification is logged to a purpose-built compliance table.

routes/flipdesk-webhooks.ts:1288-1511 · migrations/00075_ebay_account_deletion_log.sql

Rate-limit discipline is better than most applicants show

Every eBay call goes through one wrapper that honors the Retry-After header on 429 and 5xx responses instead of guessing at a backoff, trips a circuit breaker on repeated transient failures, and never retries a genuine 4xx. Bulk syncs impose bounded concurrency and a deliberate fan-out ceiling described in the code as a guardrail against the daily quota. When a sync hits a 429 it stops and reports a partial result rather than hammering.

lib/ebay-client.ts:79-106, 1879-1885, 3483-3553

No server-side scraping, and a test that keeps it that way

The sold-search URLs the app produces are deep links a seller clicks to open eBay's own completed-listings search. Nothing fetches them. A dedicated test asserts against the source that the comp worker contains no marketplace hostname, no HTML parser, no category-tree walk and no search pagination, and that the comp queue has exactly one writer. It fails the build if a crawler ever appears.

This is a genuinely good story to tell eBay. Say it in the application. It is the opposite of finding 1, which is why finding 1 has to be resolved first.

lib/sold-comps.ts:256-290 · tests/comp-read-no-crawl_test.ts

Token handling

OAuth only, no eBay credentials ever touched. Access and refresh tokens are encrypted with AES-GCM and bound to the owning user id as additional authenticated data, so a token stolen from one row cannot be decrypted in the context of another. Refresh failures distinguish a dead grant from a transient error, so a network blip does not silently disconnect a seller.

Legal surface

eBay is named in the privacy policy as a marketplace connection and in the subprocessor table with purpose, data and location. The account-deletion page tells users their eBay tokens are destroyed and points them at eBay's own revocation setting. The trademarks page carries the required wording: eBay is a trademark of eBay Inc., and this application uses the eBay API but is not endorsed or certified by eBay Inc.

A cron reconciles both notification destinations against eBay, so a destination that eBay marks unreachable gets recreated rather than sitting dead until someone notices. Application Title / Summary

GradeThread FlipDesk: AI condition grading and end-to-end listing management for pre-owned apparel resellers on eBay.

Application Details

GradeThread is a SaaS platform for people who resell second-hand clothing. Sellers photograph a garment, our AI returns a numeric condition grade from 1.0 to 10.0 with a written condition report, and FlipDesk carries that item through the rest of the lifecycle: cataloging, measurement, pricing against comparable listings, drafting, publishing to eBay, order sync, shipping and reconciliation.

How a seller moves through the app

  • Connects their eBay account through OAuth. We never see eBay credentials. Tokens are AES-GCM encrypted at rest and bound to the owning account.
  • Uploads garment photos. Our grading model returns a condition score, a defect list and a suggested eBay condition id consistent with eBay's apparel condition policy.
  • We call the Taxonomy API for the leaf category and its required aspects, and the Browse API for comparable active listings to anchor a price.
  • We create the inventory item and offer through the Sell Inventory API, apply the seller's business policies from the Account API, and publish.
  • Order and payout state comes back through Fulfillment, Finances and Marketplace notifications. Sales reconcile against the seller's inventory and cost basis.
  • Shipping is the remaining manual step, which is why we are requesting Sell Logistics.

Why the extra call volume

Publishing one listing takes roughly six calls across Taxonomy, Inventory, Account and Compliance. Our sellers are bulk operators who process N items a day, and inventory and order sync runs on a schedule on top of that. We are at X calls per day against the 5,000 default and hitting the ceiling on Y days a month, which forces us to defer publishes into the next day.

Compliance posture

  • Subscribed to eBay Marketplace Account Deletion notifications. Our endpoint verifies eBay's signature before acting, deletes the affected user's data, logs every notification, and returns a non-2xx so eBay retries if any step fails.
  • All eBay data comes from the API. We operate no crawler and parse no eBay HTML. This is enforced by an automated test that fails our build if a scraper or HTML parser is ever added to the comparable-pricing code path.
  • We honor Retry-After on every 429 and 5xx, run a circuit breaker, cap concurrency, and deliberately limit fan-out per sync to stay under the daily quota.
  • Comparable listings are shown with a link back to the eBay item page and are attributed to eBay in the interface.
  • eBay is named in our privacy policy and subprocessor list, and we carry the standard trademark and non-endorsement notice.
  • Retention: eBay data derived from other sellers' public listings expires after 90 days; a seller's own listing and order data is deleted when they close their GradeThread account or disconnect eBay.

Restricted APIs requested

  • Sell Logistics. Sellers currently leave the app to buy a shipping label and come back to record the tracking number by hand. Logistics closes the last open step, so an item goes from photo to shipped without leaving FlipDesk, and tracking lands on the eBay order automatically instead of late or not at all.
  • Buy Marketplace Insights. We price from active listings today, which are asking prices and skew high. Our own code flags those prices as estimated for exactly that reason. Sold data would let us price honestly, which means fewer overpriced listings sitting unsold on eBay. Our integration for this API is already written and is disabled behind a flag; it makes no calls without the grant.
